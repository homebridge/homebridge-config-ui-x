### ChangeLog:


- combined bridge status widgets for screen reader into one concise button, so that someone knows the status of the bridge, and can restart it easily. Before, the bridge names/statuses were shown in duplicate places for the screen reader, impacting navigation and usability.
- fixed sidebar navigation menu to keep track of the currently selected menu item/page, for the screen reader, and made the menu button label look much nicer on mobile devices.
- fixed settings screen to be more concise for screen readers, cleaning up repeated text/button labels etc. I also fixed the alert modal at the bottom when HB needs to be restarted for a settings change, so that the screen reader sees an actual "restart HomeBridge button" instead of just static text. For whatever reason this took me like 3 hours because of the way the modal is setup, and live regions etc lol.
- changed backup/restore, and config backup/restore to behave better for screen readers. Grouped "backup actions" together for each backup file (download, delete, restore) for easier navigation/usability, especially if someone has a large amount of backups to go through/look at.
- modified manage versions/plugin install screen to label the install button, label the download backup button for HomeBridge UI, and general clean up for screen readers.
- modified child bridge setup screen to label the checkbox, hide the plugin icon image from screenreader, and get rid of the static "use child bridge" text next to the checkbox (that's now the checkbox's label.) I've tried to do this consistently in many other places/modals etc across the UI.
- fixed plug-in card unlabeled links etc, and changed a few links to buttons, as that's really what they are (plugin actions, restart bridges etc)
- fixed search button to show state (expanded/collapsed), set screenreader focus on search field, and labeled the clear search button, as before it showed as an unlabeled "link."
- fixed plugin config editors to get rid of duplicate text for checkboxes, and force expandable elements to show as such to the screenreader. I tried to be careful here, because I needed to essentially re-render these elements inside of json-schema-form-patch.directive.ts, and I want to make sure I don't unintentionally hide a part of a plugin UI to the screen reader while getting rid of redundancy; so this might be something I need to take a closer look at/together etc, but I think what I've done now is fairly safe. Ideally I'd rather fix this on the actual rendering side, before it gets to that directive but it doesn't look like that's possible/easy to do, and that's ok.
- fixed unlabeled image filenames in plugin manual config, via markdown directive.
- enabled "screen reader" mode in all terminal cases; this now allows screen readers to view all logs, and interact with the terminal, both as widgets and on their respective pages. This also makes plugin installation/updates/uninstalls give spoken feedback to the screenreader, all of which was never able to be seen before from the UI.
- assigned a button/label to the gear widget settings icon, allowing the screen reader to access widget settings, which was previously always hidden to the screen reader. Also fixed redundant text for checkboxes in the resulting widget-control modal dialog.
- changed UI behavior to allow user to select/deselect multiple widgets in the show/hide panel before closing (you have to manually close the modal now) so you don't have to constantly go back and forth in and out of that dialog every time you change a widget's shown state. If you don't like this, feel free to change it back. Maybe this was intentional because of the dragging aspect? we can talk about this together :)
- added the ability for screen readers to drag widgets within the UI. Hopefully this leaves everything visually unchanged, but for the screenreader, this creates another layer, which does the following:
 - When widgets are locked, everything behaves as before.
 - when widgets are unlocked, the user is notified that widgets can be drag-able, and their settings can be changed. THere's an additional "reorder mode" toggle, which must be activated for widgets to be moved.
 - once selected, reorder mode allows the tab key to select a widget, up and down arrows to move it up or down in the list, and left and right arrows to move it to the top or bottom of the list, respectively. Escape will exit reorder mode, as well as clicking on the reorder mode button again.
 - all of the above should ideally be hidden from sighted users perspective/view. Let me know if this is not the case.
- accessories:
 - modified switch behavior for screen readers so that the switch name, type and state are in one on/off control.
 - labeled the manage accessory button as "edit (accessory-name)" for screen readers
 - removed redundant text "room name" in the add room dialog (text field is already labeled correctly) and also removed redundant close button, only for screenreader
 - reconfigured all sensors (contact/carbon monoxide/dioxide/motion etc) to be screen reader friendly (no buttons, just updating text with their status), and my goal is to reconfigure all accessory types to be screenreader friendly, and configure respective manage components to do the same, where applicable. An example of this can be seen with the door accessory, but wanted to stop there until we're more in sync with git etc. The only current caveat to this is that the announcements of sensor state change re-trigger upon re-entering the accessories page after being in a modal. So I will need to deal with that, but for now, that's ok and more of a proof of concept. Also open to suggestion here.

I need to be able to control the state name, open/closed, etc for different accessories.
